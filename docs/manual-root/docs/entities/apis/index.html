APIs

ALPHA

Why the API entity?​

In a typical API gateway setup, each HTTP endpoint is configured as an individual route. This works well for simple use cases, but as your platform grows, you end up with dozens or hundreds of routes that logically belong to the same service — they share the same backends, the same security policies, the same documentation. Managing them individually becomes tedious and error-prone.

The API entity solves this problem by providing a higher-level abstraction that groups everything related to a single API under one roof:

  • Multiple routes — define all the endpoints of your API (GET /users, POST /orders, etc.) in one place, with a shared domain and context path
  • Shared backends — define backend targets once and reuse them across routes, instead of duplicating target configurations
  • Plugin flows — create named plugin chains (authentication, rate limiting, transformations, etc.) and assign them to different routes as needed
  • Consumer plans — define who can access your API and how (API keys, JWT, mTLS, OAuth2), with pricing and quotas
  • Subscriptions — let developers or machines subscribe to your plans and receive auto-generated credentials
  • Lifecycle management — track your API from staging through published, deprecated, and removed
  • Testing mode — test draft changes safely before publishing, using a special header to access draft routes
  • Versioning and deployments — keep a history of published versions with full snapshots
  • Built-in documentation — attach pages, navigation, logos, and banners to power a developer portal

In short, the API entity turns Otoroshi from a route-level proxy into a full API Management platform: you design, secure, publish, version, and document your APIs in one place.

How it works at runtime​

When Otoroshi starts or when an API is updated, each API is converted into a set of standard NgRoute objects that the proxy engine uses for request matching and forwarding. This conversion happens transparently:

  1. Each API route's frontend paths are prefixed with the API's domain and context_path (e.g., a route with path /users on an API with domain api.example.com and context path /v1 becomes api.example.com/v1/users)
  2. Backend references are resolved — either from the API's local backends or from global stored backends
  3. The plugin flow referenced by each route is attached as the route's plugin chain
  4. Published consumer plans inject the appropriate security plugins (API key validation, JWT verification, mTLS checks, etc.) into each route automatically. Whatever the plan kind, the caller is turned into an API key consumer whose quotas and restrictions are enforced at the end of the access validation phase
  5. If testing mode is enabled, additional draft routes are generated that require a special header to access

This means you get the organizational benefits of the API entity without any runtime overhead — under the hood, Otoroshi's engine processes the same optimized route structures it always has.

APIs vs. Routes — when to use which​

Otoroshi offers two levels of abstraction for configuring your HTTP traffic, and they serve different purposes:

Routes: low-level HTTP routing​

A route is a low-level, flexible building block. It gives you direct control over every aspect of HTTP proxying: exact domain matching, path patterns, headers, the full plugin chain, backend targets, TLS settings, etc. There are no constraints — you can wire anything to anything.

Routes are the right choice when:

  • You need maximum flexibility and fine-grained control over how a specific request is handled
  • You are proxying traffic that doesn't fit the "managed API" model (static assets, internal redirects, catch-all rules, WebSocket tunnels, TCP proxying, etc.)
  • You want to set up a quick one-off reverse proxy rule without the overhead of lifecycle management

APIs: structured API Management​

An API is a higher-level, more opinionated entity built on top of routes. It adds structure and guardrails: a shared domain, a context path, a lifecycle (staging → published → deprecated → removed), consumer plans, subscriptions, versioning, deployments, and documentation.

This structure is deliberate — it trades some of the route-level flexibility for consistency and governance:

  • All routes in an API share the same domain and context path, so your URL scheme stays coherent
  • Security policies are defined as consumer plans rather than per-route plugin configurations, making it easier to reason about who has access to what
  • Lifecycle states prevent accidental exposure of work-in-progress endpoints
  • Subscriptions and credential generation provide a self-service workflow for API consumers
  • Deployment history gives you traceability of what was published and when

APIs are the right choice when:

  • You are exposing a service to external or internal consumers and want to manage access in a structured way
  • You need lifecycle management, versioning, and deployment tracking
  • You want to offer subscription plans with auto-generated credentials (API keys, JWT, OAuth2, mTLS)
  • You are building a developer portal

Under the hood, it's all routes​

The key insight is that APIs are ultimately compiled down to routes at runtime. An API is a management-layer abstraction — it doesn't introduce a different proxy engine. When you create an API with 5 endpoints, Otoroshi generates 5 NgRoute objects behind the scenes, with the domain/context path prefixed, the backends resolved, and the consumer plan security plugins injected. So the choice between APIs and routes is really about how you want to organize and govern your configuration, not about runtime behavior.

API lifecycle​

An API goes through the following lifecycle states:

staging --> published --> deprecated --> removed
StateDescription
stagingThe API is being designed. Only draft/testing routes are served (if testing is enabled).
publishedThe API is live and serving traffic. Plans can accept subscriptions.
deprecatedThe API is still serving traffic but is marked for removal. No new subscriptions should be created.
removedThe API is deactivated. No traffic is served.

An API written by a remote catalog takes its state from the source of the catalog: each deploy of the catalog is a deploy of the API, without a draft.

API blueprints​

The blueprint field indicates the type of API being managed:

  • REST: Standard RESTful HTTP APIs
  • GraphQL: GraphQL APIs
  • gRPC: gRPC services
  • Http: Generic HTTP services
  • Websocket: WebSocket-based APIs

Routes​

An API is composed of multiple routes. Each route describes an HTTP endpoint exposed by the API (e.g., GET /users, POST /orders).

A route is composed of a frontend (describing the entry point: domain, path, methods, headers), a reference to a backend, and a reference to a flow (plugin chain).

PropertyTypeDescription
idstringUnique identifier of the route
namestringDisplay name of the route (optional)
enabledbooleanWhether this route is active (default: true)
frontendobjectFrontend configuration (domains, paths, headers, methods, query, strip_path, exact)
backendstringReference to a backend ID (either a local API backend or a global stored backend)
flow_refstringReference to a flow ID from this API's flows list

The route's frontend paths are automatically prefixed with the API's domain and context_path. For example, if the API has domain: api.example.com and context_path: /v1, and a route has a frontend path /users, the effective matching path will be api.example.com/v1/users.

A route can be enabled or disabled independently of the API's activation.

Route JSON example​

{
  "id": "route_users_list",
  "enabled": true,
  "name": "List users",
  "frontend": {
    "domains": ["oto.tools/users"],
    "strip_path": true,
    "exact": false,
    "headers": {},
    "query": {},
    "methods": ["GET"]
  },
  "backend": "api_backend_abc123",
  "flow_ref": "default_plugin_chain"
}

Backends​

A backend represents a list of target servers, along with its load balancing, health checks, and connection settings.

Backends can be defined locally within the API (in the backends array) or reference a global stored backend by its ID. This makes backends reusable across multiple APIs and routes.

clientstringReference to a backend client configuration ID from clients_backend_config

Choosing the plan of a call​

Between plans of the same kind, the order of plans decides: the first one that identifies the caller wins (see several plans on the same route). A selection lets a plan pass on a call: all its conditions have to hold, evaluated against

{
  "request": { "method": "GET", "path": "/users", "domain": "my-api.oto.tools", "ip": "1.2.3.4",
               "headers": { "x-partner-id": "acme" }, "query": { "page": "1" } },
  "token": { "client_id": "client-1", "tier": "gold" },
  "certificate": { "subject_dn": "CN=client-1", "issuer_dn": "CN=my-ca", "serial_number": "1234" },
  "client_id": "client-1"
}

where token holds the claims of the token of a jwt or an oauth2-remote plan, certificate the client certificate of an mtls plan, and client_id the client id the plan read, without prefix. A plan whose selection fails for a call identifies no one, and the next plan gets the call:

"plans": [
  { "id": "plan_gold", "access_mode_configuration_type": "jwt", "selection": [{ "path": "$.token.tier", "value": "gold" }], ... },
  { "id": "plan_free", "access_mode_configuration_type": "jwt", ... }
]

Plan statuses​

A plan is served when it is published or deprecated: it installs its access plugins on the routes of the API, and its consumers are identified and enforced.

StatusOn the routes of the APISubscriptions
stagingnot served: installs nothingcan be created
publishedservedcan be created
deprecatedserved: its consumers keep calling, with their quotasno new subscription; the existing ones can be updated
closednot serveddeleted with their API keys

An API with no published or deprecated plan refuses the calls that no plugin of its flows identified (401, with apikey_rejection_reason: the api has no published plan): putting its last plan in staging, closing it or removing it never opens the API. To serve anonymous callers, publish a keyless plan (with create_if_missing: false if no API key should be stored per caller).

Access modes​

Whatever the access mode, a served plan turns the caller into a consumer, and a consumer is always an API key: the quotas, restrictions and rotation of the plan are enforced the same way for a public plan and for a plan asking for client credentials. See API consumers and plugin flows for the whole picture.

ModeDescriptionPlugins applied
keylessNo credential required. The consumer is derived from an expression, the caller IP address by defaultNgExpressionApikeyExtractor
apikeyRequires a valid API key. Configurable key patterns, restrictions, quotas, and rotationApikeyCalls
jwtRequires a valid JWT token. The consumer is the client id claim of the tokenNgJwtApikeyExtractor
mtlsRequires a TLS client certificate matching the configured subject/issuer patternsNgClientCertApikeyExtractor
oauth2-localOAuth2 client credentials flow with local token generation. Clients obtain a JWT to call other routesApikeyCalls + client credentials endpoint
oauth2-remoteOAuth2 token verified against the OIDC settings of an auth. module. The consumer is the client id claim of the tokenNgOidcApikeyExtractor

Every route of a published or deprecated API ends with NgApiConsumerEnforcer, whatever its plans. It runs at the plugin index 1000 of the access validation phase, requires a consumer, and is the only place where a call is counted against the quotas of the plan. On an API without a published or deprecated plan, it only lets through the callers a plugin of the flows of the API identified (an auth. module, an ApikeyCalls of the flow...), without enforcing their API key again: that plugin already applied its own checks and quotas.

note

The access validators run in the order of their plugin index, and the ones without an index after all the others: a plugin of a flow has to run before the consumer enforcer, with an index below 1000, for the enforcer to see the caller it identified. The plugins of a flow edited from the UI always get an index.

All the access modes but apikey and oauth2-local generate an API key for a consumer they have never seen, and they all share the create_if_missing flag for that. When it is on, the default, the generated API key is persisted and shows up in the UI. When it is off, the identity only lives for the duration of the call. In both cases the caller is served and its consumption is counted.

A jwt, mtls or oauth2-remote plan with subscription_required generates nothing: only the consumers whose subscription to the plan is enabled, and carries the client id they call with, are served. Any other caller is not identified by the plan: another plan of the API can still identify it (a keyless plan, as for any call without credentials), otherwise the call gets 401, and the analytics of the call tell which client id is not subscribed to which plan.

mTLS access mode configuration​

PropertyTypeDefaultDescription
trusted_ca_refsarray of string[]The ids of the certificates of the store (authorities) that must have signed the client certificate: its chain has to lead to one of them. Empty, the authority is not checked by the plan
regex_subject_dnsarray of string[]Regex patterns the subject DN of the client certificate may match
regex_issuer_dnsarray of string[]Regex patterns the issuer DN may match
dn_matchall or anyanyHow the two lists of patterns combine: all, every list that is not empty must match; any, one of them is enough. The backoffice writes all for a new mTLS plan
client_id_fieldstringnullDN attribute holding the client id (UID, CN, ...). Left empty, the identity is derived from the whole subject and the serial number. A certificate missing the named attribute is rejected
create_if_missingbooleantruePersist the generated API key
subscription_requiredbooleanfalseOnly the consumers with an enabled subscription to the plan, whose client_id is the one they call with, are served; the others get 401. create_if_missing is then ignored. Off, every valid token (or certificate) is a consumer of the plan
restrictionsobjectno restrictionThe restrictions of the API key of each consumer: the paths and methods it is allowed, forbidden or not found on, enforced at the end of the access validation. Changing them, or the rateLimiting of the plan, rewrites the API keys already generated for the plan

A list of patterns is satisfied when one of its patterns matches, the subject list against the subject DN of the client certificate, the issuer list against its issuer DN. With dn_match: all, every list that is not empty must be satisfied; with any, one of them is enough. When both lists are empty, any certificate is accepted, whatever dn_match says.

The authorities that may issue a client certificate are first decided by the TLS handshake, and its trust store is the one of the whole gateway: every certificate of the store plus the CAs of the JDK, unless tlsSettings.trustedCAsServer and tlsSettings.includeJdkCaServer of the global configuration say otherwise. In the permissive trust mode (tlsSettings.strictBackendServerValidation off, what an installation upgraded from a version without that field reads), the handshake accepts any client chain. A subject pattern alone then accepts a certificate with that subject from any of those authorities, and an issuer pattern only compares text with the issuer field of the certificate, which anyone can write in a certificate of their own.

trusted_ca_refs is what ties a plan to its authority. When it is not empty, the chain the client sent (its certificate, then the intermediates as sent) is validated against those certificates of the store with PKIX at the current date, before the DN patterns are read, whatever the trust store and the trust mode of the handshake. A chain that does not lead to one of them is not identified by the plan, and no API key is generated. Revocation is not checked on the chain (it is the business of the handshake and of the store), but a revoked authority is not trusted anymore: when none of the ids is a certificate of the store that is not revoked, deleted or unknown, every certificate is refused and a warning is logged. The ids are not checked to exist when the API is written, since an import or a catalog may write the API before its certificates.

{
  "access_mode_configuration_type": "mtls",
  "access_mode_configuration": {
    "trusted_ca_refs": ["partner-ca"],
    "regex_subject_dns": [".*CN=client-1.*"],
    "regex_issuer_dns": [".*CN=Partner CA.*"],
    "dn_match": "all",
    "client_id_field": "CN"
  }
}

A token refused for its issuer or its audience is not identified by the plan, and nothing is minted for it: another plan of the API can still identify the call (a second oauth2-remote plan of the same module for another audience for instance), otherwise the call answers 401. The reason is written to the analytics of the call, under token_rejection_reason.

warning

Without issuer nor audiences, the plan accepts any token signed with the keys of the auth. module: an authorization server signs the tokens of all its clients and all its resource servers with the same keys, and some multi-tenant servers sign the tokens of all their tenants with one key set. Tokens issued for other clients, for other APIs or for other tenants of the same server are accepted and turned into consumers of the plan. Set at least the audience of the API.

Validity of the keys​

With a validity, each key of the plan gets its own expiry, counted from the moment it is first enabled: the creation of an enabled subscription, or the confirmation of a pending one (the validity does not run while a subscription waits for its approval). The key gets the earlier of that moment plus the validity and the validUntil of the plan, and the start of its validity in its validity_started_at metadata.

From then on, the validUntil of the key is its own. Writing it renews or shortens the key, and that date survives the updates of the subscription and of the plan, capped by the validUntil of the plan when that one is earlier. Changing or removing the validity of the plan never extends nor resets the keys already started: it applies to the keys not started yet. Without validity, the validUntil of the plan is put back on the keys at every update, as before.

"access_mode_configuration": {
  "enabled": true,
  "validity": 7776000000
}

The keys of this plan are valid 90 days from their subscription. An api key past its validUntil is not active anymore: its calls are refused.

Rate limiting​

The rateLimiting property of a plan holds the throttling strategy handed over to every consumer of the plan, whether it got its API key through a subscription or was generated on the fly by the access mode. A plan without an explicit strategy falls back on the legacy one with the default quotas, which is what an API key created by hand gets.

{
  "rateLimiting": {
    "strategy": {
      "id": "LegacyThrottlingStrategyConfig",
      "quota": { "window": 100, "daily": 10000, "monthly": 300000 }
    }
  }
}

Subscriptions​

End-users (developers, portals, machines) can subscribe to published plans. A subscription contains information about the subscriber and references to the generated credentials (API key, certificate, JWT, etc.).

PropertyTypeDescription
idstringUnique identifier
namestringDisplay name
descriptionstringDescription
statusstringOnly enabled gives access: with any other status (pending until it is confirmed, disabled, deprecated, or a custom value) the API keys of the subscription are disabled. Defaults to disabled
api_refstringReference to the parent API
plan_refstringReference to the plan
owner_refstringReference to the subscribing client
subscription_kindstringKind of subscription: apikey, mtls, keyless, oauth2-local, oauth2-remote, jwt. It has to be the access mode of the plan
token_refsarray of stringReferences to generated credentials (API key IDs, certificate IDs, etc.), and to the shared credential the subscription shares, if any (see One API key for several APIs)
client_idstringFor a jwt, mtls or oauth2-remote subscription: the client id its consumer calls with, as the plan reads it, without prefix. See below
datesobjectLifecycle timestamps (see below)
tagsarray of stringTags
metadataobjectMetadata

A subscription is refused with a 400 when its subscription_kind is not the access mode of its plan. A subscription to an apikey or an oauth2-local plan is given an API key built from the plan, and referenced in token_refs as {"apikey": "<client id>"}: the consumers of these plans call with an API key, and a subscription is the only way to get one. The keyless access mode builds its consumer at call time, its subscriptions have nothing to generate.

The jwt, mtls and oauth2-remote access modes build their consumer at call time too, as the API key <prefix><client id> (jwt_<api id>_<plan id>_, mtls_<api id>_<plan id>_ or oauth2_<api id>_<plan id>_, the client id being the claim at client_id_path of the token, or the client_id_field of the certificate). A subscription to one of these plans with a client_id provisions that very API key, and references it in token_refs: the subscription then decides for that consumer. A key the plan already minted on the fly for it is taken over (same client id and secret), a key of another API or of another plan is not. Two subscriptions of a plan cannot share a client_id, and the client_id of a subscription cannot change (400): delete the subscription and create another one. A subscription without client_id provisions nothing, and its consumer keeps being identified at call time.

The API key of a subscription follows its status: it is enabled only while the subscription is enabled, and disabled as soon as the subscription is set to any other status. POST .../apis/{apiId}/plans/{planId}/subscribe saves the subscription pending whatever its body says, with its API key disabled: POST .../apis/{apiId}/subscriptions/{subId}/confirm enables both. Both work on the API of their path, whose rights they require: subscribe refuses a body whose api_ref or plan_ref is not the API or the plan of the path (400), and confirm does not find the subscription of another API (404).

A subscription only manages the API keys it minted: the ones whose apiRef is the subscription, and the ones minted before the API keys had an apiRef (authorized on the API of the subscription, with the metadata a subscription writes on its keys). An API key of another subscription, or an API key no subscription minted, named in its token_refs is left alone: an update of the subscription or of its plan does not rebuild it, a deletion does not revoke it, and a new subscription does not list it in its token_refs.

Deleting a subscription (by id, all of them, in bulk, or when a remote catalog or the Kubernetes job removes it) deletes the API keys it minted: its consumers cannot call the API anymore. The API key of a jwt, mtls or oauth2-remote subscription is disabled, not deleted: the plan would mint it again, enabled, at the next call. A subscription whose API keys could not be revoked is kept, and the deletion answers a 500. Removing a plan from an API deletes its subscriptions and revokes their API keys in the same way. Closing a plan deletes its subscriptions and their API keys, whatever their kind. Deleting an API deletes its subscriptions, the API keys they hold, and the API keys its plans generated for their consumers.

One API key for several APIs​

A consumer can call several APIs with one credential (one client id and one secret), each API through a subscription of its own, with the quotas, the restrictions and the plugins of its own plan. That credential is a shared credential: an API key K that belongs to the consumer and to no subscription, authorized on nothing by itself, marked with sharedCredential.owner, the owner_ref of the subscriptions of that consumer.

{
  "clientId": "K",
  "clientSecret": "...",
  "clientName": "credential of client_acme",
  "authorizedEntities": [],
  "sharedCredential": { "owner": "client_acme" }
}

A subscription shares it with an entry of its token_refs, at its creation:

{
  "api_ref": "api_orders",
  "plan_ref": "plan_gold",
  "owner_ref": "client_acme",
  "subscription_kind": "apikey",
  "token_refs": [{ "shared": true }]
}
  • {"shared": true} takes the credential of the owner of the subscription: the shared credential whose owner is its owner_ref, located where the subscription is (the same tenant, the same teams), that a subscription created (sharedCredential.minted). When there is none, it is created with the subscription, where the subscription is located: the first subscription of a consumer creates its credential, the next ones located there share it. The owner_ref is free text, and a subscription creates the credential of any owner where its author writes: the one located in other teams is never taken that way, nor is a shared credential written by hand for an owner. They are shared by the subscriptions that name them, and only a super admin writes a minted one by hand (an import, a restoration). An owner with several credentials there names the one it shares (400 otherwise). Subscriptions of an owner created at the same time in the same location share one credential too: the first one creates it.
  • {"apikey": "K", "shared": true} names the credential, created beforehand through the API keys.

The subscription gets an API key of its own, K_b, built from its plan exactly like any other, and listed next to the credential: [{"apikey": "K", "shared": true}, {"apikey": "K_b"}]. K_b is an alias: its apiRef.credential is K. The consumer calls the API of the subscription with the client id and the secret of K, and the call is identified as K_b: the throttling strategy and the quotas of the plan of the subscription (its own counter), its restrictions, its plugins, and the apiRef of the gateway events are the ones of K_b, whose apiRef.credential tells the credential the consumer called with. The backend of each API sees the client id of its own alias. Called with its own client id, an alias is refused: it has no secret of its own. The biscuit extractors and the legacy API key extractors do not resolve the credential of an alias: they find no API key for it, and the plugins of the old engine that check a secret against the API key itself (client credentials, API key auth module) refuse the one of an alias.

  • Only an apikey or an oauth2-local subscription shares a credential, one at most, and only a shared credential whose owner is its owner_ref, that no other subscription to the same API shares yet. The API key of a subscription is never shared. Otherwise the subscription is refused with a 400. Of several subscriptions sharing a credential on one API created at the same time, one only is created, the other ones are refused with a 400. The draft of a subscription shares nothing (400): its API keys are real ones, they would open the live API.
  • The author of the subscription must be allowed to write the credential, named or not: a user who cannot is refused with a 400 by the admin API, a 403 by subscribe, and cannot update or delete such a subscription either. The owner_ref, free text, is not enough. With {"shared": true}, the credential is the one located where the subscription is, created there when there is none: the author must be allowed to write API keys there, whether the credential exists yet or not.
  • The shared entry is given at the creation and never changes, nor do the API and the owner of the subscription (400): delete the subscription and create another one.
  • The credential is its own: its secret, its rotation, its expiry and its enabled flag are set on K, and are the ones of every call. A new secret of K calls every API, and a disabled or expired K calls none, like any API key. The validity of the plan of a subscription applies to its alias, which has no rotation.
  • Suspending, closing or deleting a subscription disables or deletes its own alias only: the other APIs are still called. The credential is never updated, disabled or deleted with a subscription, not even with the last one: it is deleted by hand. Deleting K, by any means, deletes its aliases. The subscriptions that shared K stay, without an alias: they call nothing, and are still updated and deleted by the ones who can write them. They still name K and their alias: only a super admin can create an API key under the client id of a credential that aliases still name, or under a client id such a subscription still names (an import, a restoration).
  • An API key is created as a shared credential, with no authorizedEntities and no apiRef, and stays one, for the same owner (400). apiRef.credential is written by the subscription that mints the alias, and never changes (400). An alias only serves while its credential is a shared credential, the subscription named by its apiRef exists, shares that credential and lists the alias in its token_refs, and on the API it is authorized on: an alias written through the API keys (which requires the rights to write its credential) serves nothing.

A call made with K looks for its alias on the API in the proxy state, next to the API keys: it never reads the datastore, and a call that uses no alias costs what it cost before. An alias serves once the proxy state is synchronized, like any new API key.

The jwt, mtls and oauth2-remote plans need none of this: one token or one certificate already calls several APIs, each plan identifying the consumer with an API key of its own.

Testing​

The testing configuration allows you to test draft routes before publishing the API. When testing is enabled, Otoroshi generates special routes from the API's draft with a custom header requirement.

PropertyTypeDescription
enabledbooleanWhether testing mode is active
headerKeystringHeader name required to access draft routes (default: X-OTOROSHI-TESTING)
headerValuestringExpected header value (auto-generated UUID)

When testing is enabled:

  1. Draft routes are built from the latest saved draft of the API
  2. Each draft route requires the testing header (X-OTOROSHI-TESTING: <value>) to be accessible
  3. This allows you to test changes without affecting published routes

Trying a request on a route of the API​

The admin API sends a request through a route of a published or deprecated API and answers its response with the execution report of the call, like the tester of the backoffice. It is the way to see, from a script or a CI pipeline, which plan extractor identified the caller, why the api consumer enforcer refused it, and which plugins of the plan ran:

curl -X POST 'http://otoroshi-api.oto.tools:8080/apis/apis.otoroshi.io/v1/apis/my-api/routes/route_list_users/_tryit' \
  -u admin-api-apikey-id:admin-api-apikey-secret \
  -H 'Content-Type: application/json' \
  -d '{
    "headers": {
      "Otoroshi-Client-Id": "my-client-id",
      "Otoroshi-Client-Secret": "my-client-secret"
    }
  }'

Without a path, the request calls the path of the route under the context path of the API. The admin API key has to be able to read the API. The routes of an API in staging, a route of another API, or a route the API does not hold are not found (404).

The extractors of the plans and the api consumer enforcer are access validators: the call-access-validator-plugins step of the report lists each of them, allowed or denied with the status of the refusal. The request is sent from 127.0.0.1, which is what the ${req.ip} expression of a keyless plan sees. The body of the trial and the rest of the report are described in trying a request on a route.

Deployments​

Deployments track the history of API publications. Each deploy of the draft (POST .../apis/{apiId}/deployments), and each write of an API managed as code (by a remote catalog or an outside tool) that changes what is live, adds a deployment record first in the deployments of the API.

PropertyTypeDescription
idstringUnique identifier
apiRefstringReference to the API
ownerstringWho performed the deployment
atnumberTimestamp of the deployment
apiDefinitionobjectSnapshot of what was deployed: the routes, backends, flows and documentation of the API, and its plans (their access modes, quotas and plugins decide who gets in and how much)
versionstringVersion of the API at deployment time
refstringThe identifier, in the tool that deployed, of the version deployed: a commit sha, a release number, a tag. Kept from the body of POST .../deployments, taken from the deployment_ref metadata of the API for the deploys of a remote catalog. At most 256 characters, null when not given

deployments[0].ref tells which version of the source is live. The API keeps the last otoroshi.apis.deployments-history-size deployments (env. OTOROSHI_APIS_DEPLOYMENTS_HISTORY_SIZE, 5 by default). The full history is the stream of ApiDeploymentEvent sent to the data exporters, each one with the deploymentId and the ref of its deployment.

APIs managed as code​

A tool that holds the desired state of its APIs (a GitOps pipeline, a deployment job of a CI, any declarative tool) writes them as code: it marks each API it manages with its own id in metadata.created_by, external=<tool id>, and every write of such an API through the admin API is a deploy, without any draft. A remote catalog does the same with remote_catalog=<catalog id>.

  • The API takes the state of the body: it can be created directly in published, and its routes are served once the proxy state is synced.
  • The fields locked in production (domain, contextPath, routes, backends, flows, documentation, testing) take the content of the body in one write.
  • The state transitions are the ones of a deploy: a published API cannot go back to staging, and a removed API has to be reopened in staging first.
  • The deployment history and the secret of the testing header stay the ones of the live API, whatever the body holds.
  • A write that changes what is live (one of the locked fields, the plans, or the metadata.deployment_ref of the body) adds a deployment owned by the value of created_by, and sends its ApiDeploymentEvent. The same body written again adds none.
  • Such a write needs the right to write the API, nothing more.

The id of the tool is made of letters, digits, ., _ and -, starts with a letter or a digit, and is at most 128 characters long: another value is refused with 400 invalid_created_by. A remote catalog never takes over an API managed by an outside tool: an API of its source with the id of such an API is refused, and reported in the deploy report, and the undeploy of the catalog leaves it.

{
  "id": "my-api",
  "state": "published",
  "metadata": {
    "created_by": "external=my-gitops-tool",
    "deployment_ref": "3f9c2e1"
  },
  ...
}

Admin API​

The API entity can be managed through the admin API:

GET    /api/apis                     # List all APIs
POST   /api/apis                     # Create a new API
GET    /api/apis/:id                 # Get an API by ID
PUT    /api/apis/:id                 # Update an API
DELETE /api/apis/:id                 # Delete an API
PATCH  /api/apis/:id                 # Partially update an API

A request can be tried on a route of an API:

POST   /apis/apis.otoroshi.io/v1/apis/:id/routes/:routeId/_tryit   # Try a request on a route of an API

Subscriptions are managed at:

GET    /api/api-subscriptions        # List all subscriptions
POST   /api/api-subscriptions        # Create a subscription
GET    /api/api-subscriptions/:id    # Get a subscription
PUT    /api/api-subscriptions/:id    # Update a subscription
DELETE /api/api-subscriptions/:id    # Delete a subscription
